# 工程纪律基线(appendix/engineering.md)

环境未安装 implement 类技能时,执行者(子智能体/agent)按本基线执行实现流程。若已安装对应技能,以该技能为准。项目自己的规则(AGENTS.md、`.rules/` 等)与测试纪律始终优先于本基线。

## 实现前

1. 通读任务材料:ticket/任务书、spec(如有)、涉及的既有代码、项目规则;
2. 实现方案自行研究,不在派发对话里展开细节;
3. 确认授权文件清单——只改清单内文件,清单外需求停下上报(派发引擎写 QA 文档;工作流引擎经 escalation 直问),不越权改。

## 实现中

1. **在可测试的缝隙上工作**:每个功能点先找到能验证它的测试或命令,再动手;
2. **只跑直接相关测试**:不自主运行全量测试套件(需要全量时建议、由管理员/用户决定);
3. 定期运行直接相关测试,保持可回退的小步提交;
4. 提交纪律:提交信息遵循项目规则的前缀/格式惯例,一次提交做一件事。

## 交付前自查(必做,各审查路与管理员验收不替代这一步)

1. 逐条核对任务书/票面的验收预期,确认每条可指认证据(测试通过输出、产物路径、截图);
2. 自查代码:正确性(bug/边界)、安全(注入/越权/敏感信息)、一致性(命名/风格与既有代码协调)、遗漏(任务范围内的边角);
3. 环境有 code-review 类技能则跑一遍,没有则按上述清单人工过;
4. 汇报改动文件清单、提交清单(`git log` 摘要)、测试结果(哪些通过、哪些没跑及原因)、遗留问题——如实,不夸大,不以"代码写完了"判定完成。

## 敏感纪律(始终生效)

凭证/token/key 只按约定路径读取使用,内容绝不进代码、文档、汇报;不把 `.env` 等未跟踪资产的内容写进任何产出物。
