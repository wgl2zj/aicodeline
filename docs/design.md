# 设计理念(design.md)

aicodeline 的核心是一条纪律:**一个 AI 干活,另外几个互相不知情的 AI 独立验收,人不验收只终裁**。本文说明为什么这样设计。

## 管理员不干活

主智能体(管理员)只做派发、核对、裁决,不实现、不代审。依据是经验性的:编写者在实际使用中反复观察到,主智能体亲自复核自己的派发成果时,受确认偏误(自己安排的方案自己看不出问题)与注意力分散(同时盯多个外勤)影响,行为缺陷的独立发现率趋零。这不是论文结论,是把"写的人不审、审的人不知道写的人怎么想"这条工程界老规矩搬进多 AI 协作。

## 审查为什么强调"独立"与"异构"

- **独立会话**:审查者全新开工,只拿客观材料(改动清单、测试输出、路径),不拿管理员的预判和倾向——拿到的材料一样,但"不知道别人怎么想"本身就是一种保护(防锚定)。
- **异构模型**:路 A 审核者与管理员、执行者用不同模型,是承认"同一家模型有同一家盲区"——换个牌子的眼睛看,才叫第二双眼睛。
- **两路/三路互不知晓**:路 A 与路 B 的提示词刻意保持一致(同材料、同要求、同格式,只有角色名不同),且互相看不到对方结论——信息差或要求差会让两路的发现面不对等,双审就失效了。

## 路 B 为什么要求"构造性验证"

复跑执行者的测试全绿只说明"执行者自证清白",不说明"没有别的形态会坏"。所以路 B 每轮必须构造至少一个执行者测试未覆盖的新形态探针或负向对照(比如把修复代码临时还原看测试是否变红、并发注入、跨模块交叉场景),给出修复前后的行为对比。这是从"验证已知"到"探索未知"的最低要求。

## 路 C 为什么是"另一台机器"

路 A、路 B 再独立也是 AI 会话;路 C 是独立进程、独立凭证的审查工具,与所有 AI 零共享上下文——不吃派发材料、不知晓任何结论,防锚定天然成立。它只覆盖代码缺陷(bug/安全/性能/风格),不覆盖行为与视觉,所以定位是"增益"而非"替代":失败可降级留痕,但 A/B 不可省略。

## 工作流引擎为什么"两段式"

工作流版把"执行+审查+机械聚合"放进一个后台 run 自动推进,但**终裁永远留在 run 外的管理员**:脚本内的"通过"只是候选放行(管理员可否决),冲突或轮次用尽标记待裁定交回,合并只发生在管理员终裁之后。机械的部分(阻塞即返工、全部重跑)交给脚本,需要判断的部分(冲突裁定、定级升降、放行)留给人——这是"裁决权不可让渡"在两段式下的翻译。

## 一些数字

返工轮次上限 3 与路 C 后台超时 20 分钟(两本工作流手册)、路 C 连续失败停下检查(工作流版按票计、派发版按次计,均为 2)、执行者心跳 10 分钟(仅派发引擎)——都是经验值,可按需调整;调整时注意四手册同步。
