# aicode-mainother-workflow —— 专票批量 · 工作流引擎版(试点)

把一次票任务装进工作流 run。与原版 aicode-mainother 的分工只在一处:**执行引擎**——原版由管理员在主会话逐次派子智能体(QA 文档轮转、心跳盯梢);本版由一个后台 run 自动驱动一整个梯队的"执行+三路审查",管理员在 run 边界外终裁合并(两段式)。角色定义、三路审查设计、任务书纪律与原版同源,以本技能为准的差异见第 7 节。

## 0. 定位、分工与试点纪律

- **同源分工**:aicode-mainother(子智能体派发,成熟)= 默认;本技能(工作流引擎,试点)= 用户点名或明确要后台自动推进/失败保底/逐项打点时;任意单任务 → aicode-mainother-general(-workflow);统一入口 aicodeline。
- **试点纪律(首次使用必须执行)**:先用 1 张非视觉小票试跑一个 run,验证四件事——①模型名册各就各位(阶段卡片/日志显示的模型与四问答案一致);②路 C 适配在本机真实可用(第 3 节);③escalation 通路顺畅(自然或人为触发一次,管理员能收到并答复);④run 结束返回材料与验收报告完整。四项全过再上全量票。
- 试点期内本技能与原版并存;用户未点名引擎、也未提出上述需求(后台自动推进/失败保底/逐项打点)时,不主动选用本技能。

## 1. 角色与铁律(两段式)

**第一段(run 内,脚本机械驱动)**:逐票派发执行者 → 交付后并行派出路 A、路 B 审查 agent + 后台跑路 C 机器闸门 → 机械聚合 → 打点汇报;返工循环带轮次上限。

**第二段(run 外,管理员=主智能体)**:启动前外勤(四问、占票、预建工作树、写名册与脚本、确认启动)+ run 期间应答 escalation + run 结束后终裁、纪律核对、合并、收尾、QA 结论记录、梯队推进。

**执行侧**(run 内 agent,按票路由):视觉任务执行者(视觉实现+看图自验,交付附截图证据路径)/非视觉任务执行者。

**审查路**(三路相互独立、互不知晓对方结论):
- **路 A · 异构审核**(问 3 模型):模型须与管理员及执行者异构;含视觉票时须多模态亲自看图。
- **路 B · 独立复核**(执行者模型的独立会话):方法硬要求=构造性验证(见第 3 节任务书)。执行者模型非多模态时为**复合复核**——非视觉维度由执行者模型独立会话承担,视觉维度由问 4 模型看图,两份结论由脚本整合为一份路 B 材料;视觉维度 agent 不接管路 B 整体。
- **路 C · 机器初审**(world.run 机器闸门,非 agent):代码缺陷机械全覆盖与行级定位;可降级留痕(第 3、6 节)。

五条铁律(与原版同源,两段式翻译):

1. **管理员不越界**:run 内由脚本机械驱动,管理员的 run 内职责仅限应答 escalation 与必要的运行性处置(停滞重开/方向修正/停止处理)——不做冲突裁定、不做升降级、不执行合并;其余职责为外勤、终裁、纪律核对、合并、收尾等;不替子智能体研究实现方案、不代写代码、不亲自承担行为审查(设计依据:编写者实测主智能体亲自复核受确认偏误影响明显,行为缺陷独立发现率趋零,详见包内 docs/design.md)。
2. **escalation 是唯一问答通道**:run 内子智能体遇阻经工作流提问机制直问管理员,管理员答复后其原地继续;需用户决策的问题由管理员在主对话问用户,再回填答复。原版 QA 停机轮转(status: waiting-main → 唤醒)在本引擎下废止。**若 escalation 暴露的是脚本结构问题**(闸门无法通过、流向错误),不修答案,改脚本后 AmendWorkflow 重发(第 6 节)。
3. **QA 结论记录一票一份**:管理员在派发前建骨架,终裁后填写(第 5 节);不再是状态机轮转文档,不承载问答;禁令照旧——记录中不得出现凭证、token、key、`.env` 内容。
4. **一律工作树,无豁免**:所有修改必须在独立工作树内进行(操作规范见 appendix/worktree.md 或环境已装的 worktree 类技能);并行多票由管理员启动前预建各树(串行建、时间戳错开),路径写入脚本常量与各任务书;gitignore 资产照旧"复制清单:复制进树、收尾删副本";禁止以"要用真实 API/凭证"为由留在主工作区改。
5. **三路审查+管理员终裁**:验收=路 A+路 B+路 C 三条独立审查+管理员亲自的纪律核对与终裁。路 A/路 B 不可省略、不可降级;路 C 可降级但必须留痕。脚本内的"通过"仅为**候选放行**(管理员可否决);冲突或轮次用尽的票标记**待裁定**交回;裁决权永远在管理员。

## 2. 启动:身份自判 + 四问 + 依赖分梯 + 外勤

1. **身份自判**:管理员自判模型身份(是否具备视觉能力;决定视觉路由与异构校验基线):优先按用户自己的全局规则,无则按本包入口的视觉路由默认约定。
2. **四问**(AskUserQuestion,每问带推荐;推荐值优先取 defaults.md 登记项,未登记时从 ListModels 列出的本机可用清单按各问条件筛出,不可用时换荐并说明):
   1. **非视觉执行者模型**:逻辑/数据/文档部分的执行者;推荐可用强模型。
   2. **视觉执行者模型**(本轮含视觉票时必问):须多模态;推荐多模态候选(须能亲自看图,产出+看图自验一体)。不得套用问 1 答案;视觉子任务打包档位按本包入口视觉路由约定执行(用户自有全局规则优先)。
   3. **路 A 审核者模型**(每轮必问,全轮复用):须同时满足——①**模型异构**(与管理员及问 1/问 2 已选执行者都不同模型);②**多模态门槛**(本轮含视觉票时审核者自身必须多模态)。从本机可用清单按①②筛出候选推荐。候选不满足①②时说明不满足项并重新问。
   4. **路 B 视觉维度模型**(仅当本轮含视觉票且**执行者模型**非多模态时问):须①多模态;②不得与问 3 同一模型。推荐多模态候选,不可用时降级推荐其它;与问 2 同模型时相当于执行者同模型自审,条件允许时建议选异构候选。
   四问答案写入脚本**模型名册**(第 3 节),**启动后锁定**;中途换模型=改脚本重发(AmendWorkflow,已完成步骤缓存回放,代价低)。
3. **依赖分梯**:逐票读 ticket 的 `Blocked by` 并核对隐性耦合(共享文件/目录、接口契约、数据库迁移、前后端咬合),形成"票 → 前置"依赖图;相互无依赖且文件域不重叠的票组成**一个梯队=一个 run**(前置票验收合并后解锁下梯队);硬规则照旧——同一时间只允许一张票产出数据库迁移文件。单票或天然串行退化为单票 run。
4. **外勤(管理员做,主工作区)**:核票+视觉/非视觉分类扫描(按产出物性质路由,"复刻既有形态/断言锁死/无设计空间"不构成豁免);占票(`Status: claimed`,`.scratch/` 归管理员维护);预建本梯队各工作树;建 QA 结论记录骨架+更新 `QA/INDEX.md`;路 C 前置自检(按 defaults.md 登记的机器初审提供者命令跑连通性自检,带新生成会话标识;未登记时先完成接入,范例见 examples/,或由用户决定本轮免路 C)。
5. **写脚本并启动**:按第 3 节规范实例化脚本,CreateWorkflow 提交;**确认框=开工计划一次性确认**(用户看到阶段图、命令集与脚本全文)。确认后 run 自动推进到本梯队终态,不再请示(阻塞类例外见第 5 节第 5 条)。

## 3. 工作流脚本规范

**模型名册与票据清单(骨架)**:

```ts
// 模型名册:四问答案(推荐值优先取 defaults.md);启动锁定。ids 来自 ListModels。
const MODELS = {
  executor: model("<问1:非视觉执行者>"),
  visual: model("<问2:视觉执行者,含视觉票时>"),
  auditor: model("<问3:路A,异构>"),
  bVisual: model("<问4:路B视觉维度,条件启用>"),
};
// 本梯队票据(管理员外勤时已核定):{ id, ticket路径, 工作树, 分支, visual }
const TICKETS = [/* … */];
```

**阶段图(用户在确认框看到的开工计划)**:

```ts
phase("读取票据并派出本梯队执行者");   // files 读票核对 + 首批 ask
phase("逐票执行,交付后三路审查与机械聚合");  // 每票流水线(fan-out 内不再标 phase)
phase("汇总验收材料交管理员终裁");      // artifact.markdown 发布 + return
```

**每票流水线(fan-out 内)**:返工循环**轮次上限 3**;每轮——执行者交付(类型化结果:改动文件清单、提交清单、测试结果、截图证据路径、遗留问题)→ `Promise.all` 并行派路 A、路 B(互不知晓;路 B 复合复核时拆两路)→ 后台跑路 C → 机械聚合:

- 任一路**阻塞**级 → 聚合阻塞清单作为 feedback,返工重走三审(全部重跑,不因"只改了一点"只重跑一路);
- 全部"通过/建议" → **候选放行**,跳出循环;
- 轮次用尽 → **待裁定**交回。

每轮 `report()` 打点到看板(票号、轮次、三路结论摘要),失败保底;路 C 连续 2 票失败 → run 内停派路 C 并在 return 标注,run 结束后管理员用新生成会话标识重跑提供者连通性自检,检查命令与凭证配置(多为额度/网络问题),修复或经用户确认免路 C 后再继续后续梯队。

**执行者任务书**(五件事,不讲实现细节):①用什么方法——实现流程优先用环境已装的 implement 类技能、工作树流程优先用 worktree 类技能(给 SKILL.md 绝对路径,run 内 agent 无法经 Skill 工具触发,自行读取等效遵循;未装时按本包 appendix/engineering.md 与 appendix/worktree.md 两份基线执行);交付前先自行做一遍代码自查(环境有 code-review 类技能则用之)并修复发现的问题(各审查路与管理员验收不替代这一步);项目规则(AGENTS.md、`.rules/`)与项目测试纪律照常适用;②做哪票——ticket(及 spec)绝对路径;③工作树路径与分支、复制清单;④身份与视觉自验——视觉执行者交付必须附每项预期的通过/不通过+图中可见证据(截图文件路径);⑤四条行为纪律(内联)——全量回归禁令(只跑与票直接相关的测试)/只读边界(不碰 `.scratch/` 与主工作区,修改限树内,复制清单是唯一例外)/敏感纪律(凭证只按约定路径读取,内容不进代码文档汇报)/**遇阻经 escalation 直问管理员,不再写文档停机**。

**审查任务书(路 A/路 B 必须一致)**:同材料清单、同审查要求、同纪律、同输出格式,仅角色标识不同——先写一份中立模板再复制改角色段,禁止给任一路增删要求。材料只给客观事实——ticket 路径、工作树路径与分支、改动文件清单、测试输出、截图证据路径——**不得包含管理员预判、倾向或已发现的问题**(防锚定)。共同纪律:只读边界(可运行只读命令与直接相关测试复核,不修改任何文件,修复不归审查者管)、分级输出(**阻塞/建议/通过**,每条附证据:文件行号、测试输出;视觉票必须亲自看图,写明截图位置与预期差异)、遇阻 escalation;审查结论以类型化结果交回脚本,汇总进返回材料与验收报告(替代原版 QA 区块落盘)。路 B 复核内容五项:①四要素核对——改动文件清单、提交清单(`git log 主分支..工作树分支 --oneline`)、测试结果(哪些通过、哪些没跑及原因)、执行者遗留问题清零;②抽查核实——亲自读关键 diff、亲自跑直接相关测试(不自主全量回归);③行为预期核对——按 ticket 勾选项逐条验收,新功能行为预期确认已配测试锁定;④断言全集核对——改动涉及共享标识(表结构/表头文案、注册表/枚举集合、与既有标识同前缀的新键名)时,`grep -rn "<被改标识>"` 列出断言全集,逐条三选一显式处理:已同步 / 语义不变显式豁免 / 守卫已改单词边界防子串误伤,未做的退回补齐;⑤**构造性验证下限**——每轮至少构造一个执行者测试未覆盖的新形态探针或负向对照(形态参照:移除/还原修复代码的对拍、并发或边界注入、跨实例重建的多步用户序列、跨模块交叉场景),给出修复前后行为对比;复跑执行者测试全绿只是门槛,不是通过结论;无构造性验证的报告退回重做。

**路 C 机器闸门(world.run 适配,试点必测;可插拔提供者)**:

- **提供者接口约定**:输入＝分支 diff(主分支 → 工作树分支);输出＝分级缺陷清单(critical/high/medium/low,行级定位);运行要求＝独立进程、独立凭证、会话标识每次新生成不得复用。命令形态从 defaults.md 的机器初审段带出;未登记时先探测本机可用审查 CLI,探测不到则询问用户接入(接入范例见 examples/provider-opencode-review.md,含 env 包装注入环境变量、uuid 经 `world.run("node", ["-e", "console.log(crypto.randomUUID())"])` 取等 world.run 适配细节)或本轮免跑;
- **cwd 限制**:world.run 固定在主工作区执行,无法 `cd` 进工作树——启动前用 EvalWorkflowSnippet 实测所选提供者是否支持目录参数;diff 已由分支参数界定,输出路径用绝对路径,通常不受影响;实测有阻则在 QA 记录差异并按降级处理。
- 输出语言:中文;仍输出英文则先补设提供者配置再重跑。
- 时序与超时:与路 A/路 B 派发同时后台启动;后台超 20 分钟无产出视为超时,按降级处置。可向提供者附业务背景参数(仅中立事实、取自 ticket 原文)。
- 结果归并:critical/high=候选阻塞逐条核实、medium=候选建议、low 忽略(噪音多);其行号可作两路报告行号存疑时的参照基准;**路 C 通过不替代任何一路**;失败/超时 catch 降级留痕(路 A+路 B+管理员核对已满足硬规则),不阻塞;纯文档/纯注释票豁免并记录。
- 范围与泄漏面:只审工作树分支相对主分支的已提交 diff——复制清单的未跟踪文件(`.env` 等)天然不在其视野。
- 树内测试等命令同理:优先让 agent 自跑(其 Bash 无 cwd 限制);必须脚本闸门时用命令自带目录参数(`git -C`、`npm --prefix` 等),启动前实测。

**返回值**:WorkflowReport 形态(conclusion+findings[各票:状态(候选放行/待裁定/failed)+三路结论摘要+证据]+verified+notCovered),并以 `artifact.markdown` 发布完整验收报告(供 run 后终裁使用)。

## 4. run 期间管理员职责

- **不轮询、不等待**:完成/异常通知自动到达;期间可干别的。
- **escalation 应答(三分类)**:①事实澄清/材料补齐 → ResolveWorkflowQuestion 直答;②需用户决策 → 主对话问用户后回填;③脚本结构问题 → 改脚本 AmendWorkflow 重发(第 6 节)。
- 收到 stall 通知(20 分钟无进展)= 信息性,run 仍在跑,不需处置。若疑似长期卡住且无 escalation:用 GetWorkflowRun 看快照确认——在跑则继续等;确认停滞则停止该 run,带材料缩小任务重开。

## 5. run 结束:终裁、合并、收尾、QA 结论记录

1. **逐票终裁(不可让渡)**:读返回材料+验收报告 → 候选放行可否决;待裁定必裁定;冲突显式裁定并写明理由;可依纪律核对与客观材料对任一路定级升降(附证据)。
2. **纪律与结构核对(亲自,不可委托)**:diff 范围核对(无范围外夹带)、边界核对(主工作区无越权写入、无现场污染)、敏感核对(凭据零泄漏)、台账核对(票据勾选与 Status、QA 记录、提交清单一致)。
3. **QA 结论记录(终裁后填写)**:关键决策、三路验收结论与冲突裁定、路 C 降级/豁免、返工轮次;结论性内容摘录进 ticket 的 `## Comments`;更新 `QA/INDEX.md`。
4. **合并与收尾**:逐票串行合并(优先 `--ff-only`,不能快进则 `--no-ff`;冲突不自行解决,列清单交用户)→ 按复制清单删树内副本 → `git worktree remove` → 清 upstream 删分支 → `git worktree prune`;ticket 勾选验收项、`Status:` 置 done/resolved。
5. **梯队推进**:本梯队全部终态后,按第 2 节开下一梯队 run;全程唯一开工类确认点=每次 CreateWorkflow 确认框(escalation 中需用户决策的问题、合并冲突清单、审查路能力缺失等阻塞事项照常停下问用户)。
6. **最终统一汇报**(所有票终态后):各票改了什么、跑了哪些测试、验收情况(A/B/C 结论、冲突裁定、路 C 降级/豁免、返工轮次)、合并与清理结果、失败与重派、是否建议全量回归。

## 6. 失败处置

- **provider 停止**(登录过期/模型不在计划/额度耗尽,通知的 `<error>` 会点名原因):停下与用户修因 → 修好后续跑(AmendWorkflow 或 ResumeWorkflowRun,同一 run 内已完成步骤零成本回放,不重写重来)。
- **脚本 errored**(通知点名脚本文件):Edit 修复该文件 → AmendWorkflow(path)重发;**不**用 CreateWorkflow 从头重写。
- **run 方向不对**(用户指出或打点显示):立即 AmendWorkflow(不等跑完、不先 TaskStop),越早越省。
- **用户主动停止**:问清意图再动,不擅自续跑。
- **审查路能力缺失**(异构候选不可用等):停下问用户并推荐满足条件的替代模型,不得静默降级为单路放行。
- **执行者失败**:脚本标记 failed 交回,管理员带材料缩小任务重开;失败不甩锅,最终汇总如实汇报。

## 7. 与原版 aicode-mainother 的已知差异

1. **确认节奏**:原版全程一次开工确认 → 本版每 run 一次(CreateWorkflow 确认框,含阶段图与命令集);梯队制下=每梯队一次。
2. **问答机制**:QA 文档停机轮转 → escalation 直问、原地继续;QA 降级为终裁后结论记录。
3. **心跳盯梢**:删除——provider 临时错误由运行时自愈;停滞兜底见第 4 节(stall 通知本身不需处置,长期停滞经 GetWorkflowRun 确认后停止重开)。
4. **模型管理**:四问答案=启动锁定的模型名册;换模型=改脚本重发(缓存回放),原版可轮次间换子智能体类型。
5. **路 C 形态**:管理员外勤 CLI → 脚本 world.run 机器闸门(结果由 exit code/输出决定);受 cwd 限制,启动前须实测适配;路 C 连败 2 票的处置由原版"当场停下检查"变为"run 内停派标注、run 后检查修复"(两段式时机所致)。
6. **合并时机**:原版逐票"验收即合并" → 本版 run 边界后管理员逐票串行合并(合并仍逐个串行,时机点后移到 run 终裁后)。
7. **主对话安静度**:进度看 run 面板/阶段图/逐轮打点,不轮询;原版靠管理员盯 QA 文档与心跳。
