# aicode-mainother —— 管理员 + 三审查路（票据批量编排）

把一次票任务装进子智能体。主智能体担任**管理员**：只管派发、核对纪律、终裁——不实现、不代审。

## 票据格式约定

本模式面向 **.scratch 票据批量**:每票一个 Markdown 文件,含 `Status:`(open/claimed/done/resolved/failed)、`Blocked by:`(前置票号)、逐条验收勾选项、`## Comments`(结论摘录留档)。兼容 Matt Pocock 技能集(to-tickets)产出的票据;任何同格式票据均可,不依赖其安装。

## 0. 角色与铁律

**管理员**（主智能体）：派发任务（先做视觉/非视觉分类路由）、启动三条审查路、纪律与结构核对、综合裁决与冲突裁定、解答子智能体提问（经 QA 文档）、执行合并与清理。不替子智能体研究实现方案、不代写代码、不亲自承担行为审查——设计依据:编写者实测主智能体亲自复核受确认偏误影响明显,行为缺陷独立发现率趋零(详见包内 docs/design.md)。

**执行侧**（产出交付物）：
- **视觉任务子智能体**：一切涉及视觉的任务——UI 实现、样式美化、UI 视觉验收、看图理解、OCR、设计稿还原，含看图自验。
- **非视觉任务子智能体**：逻辑、数据、文档等非视觉任务。

**审查路**（验收的输入，三条相互独立、互不知晓对方结论）：
- **路 A · 异构审核**（审核子智能体，问 3 拍板）：独立第一路审核，模型须与管理员及执行者异构。
- **路 B · 独立复核**（复核子智能体，选型规则见问 4）：第二路独立复核；方法硬要求＝构造性验证（见第 7 节）。执行者模型非多模态时按**复合复核**运行（机制见第 7 节）。
- **路 C · 机器初审**（可插拔审查工具,非子智能体,管理员运行）:代码缺陷的机械全覆盖与行级定位;可降级留痕（见第 7、9 节）。

五条铁律（细则见对应章节）：

1. **管理员不越界**：只做派发、分类路由、纪律核对、裁决、QA 答复及必要外勤（建 QA 文档、维护索引、执行合并、清理现场）；不在主对话展开任务细节。
2. **QA 文档是唯一问答通道**：管理员与子智能体之间的一切问答、状态变化都写 QA 文档，会话消息只传"去看文档/继续工作"。管理员是唯一答复方；需用户决策的问题由管理员在主对话问用户，再以管理员名义写入文档。
3. **QA 文档一票一份，写入权分档**：管理员在派发前建立；管理员与该票执行者可写全文；路 A/路 B 审查者各自仅可追加自己的报告区块（见第 5 节），其余部分只读；写入权不给这几方以外的任何子智能体。
4. **一律工作树，无豁免**：所有票的修改必须在独立工作树内进行——多任务并行的隔离靠它;建树与收尾按 appendix/worktree.md 工作树操作规范(或环境已装的 worktree 类技能)。需要 gitignore 资产（`.env`、凭证等）的票照常进树，按"复制进树、收尾删副本"处理（第 3 节）；禁止以"要用真实 API/凭证"为由留在主工作区改。
5. **三路审查＋管理员终裁**：每票验收＝路 A＋路 B＋路 C 三条独立审查＋管理员亲自的纪律核对与终裁。路 A/路 B 不可省略、不可降级；路 C 可降级但必须留痕（第 9 节）。各路报告只是输入，裁决权永远在管理员。

## 1. 启动：身份自判 + 四问用户

任务开始时，管理员自判模型身份(是否具备视觉能力):优先按用户自己的全局规则,无则按本包入口的视觉路由默认约定(默认视为非视觉,视觉任务一律委托);随后列出当前环境所有可用子智能体类型及定位(结合 defaults.md 已登记项),用 AskUserQuestion 问以下事项（每问必带推荐;推荐值优先取 defaults.md 登记项,未登记时从本机可用清单按各问条件筛出;条件不满足的问题可跳过,不要默认）：

1. **非视觉执行者用哪个**：本票/本轮逻辑/数据/文档部分的执行者。推荐通用执行型候选(工具齐全者优先)。不同票可选不同执行者。
2. **视觉执行者用哪个**（本轮含视觉票时必问）：推荐多模态候选（须能亲自看图,产出＋看图自验一体）。此答案确定视觉子任务的实现归届;打包档位按本包入口视觉路由约定执行(用户自有全局规则优先);**不得把问 1 的答案套用到视觉子任务**。
3. **路 A 审核者用哪个**（每轮必问，全轮复用）：须同时满足——**① 模型异构**：与管理员及问 1/问 2 已选执行者都不同模型（异构视角是路 A 的存在理由）；**② 多模态门槛**：本轮含视觉票时审核者自身必须多模态（视觉票的路 A 审核必须亲自看图，视觉维度要有两双异构的眼睛）。从本机可用清单按①②筛出候选推荐;候选不满足①②时说明不满足项并重新问。
4. **路 B 的视觉审核子智能体用哪个**（仅当本轮含视觉票且**执行者模型**非多模态时问——判断对象是执行者，与管理员自身模态无关；此时路 B 按第 7 节复合复核运行，本问只选定其中的视觉维度承担者，**它不接管路 B 整体**）。条件：**① 多模态**（必须亲自看图）；**② 不得与问 3 同一模型**（否则视觉维度两路同模型，塌缩成单模型眼睛）。推荐多模态候选,不可用时降级推荐其它;与问 2 同模型时相当于执行者同模型自审，条件允许时建议选异构候选；候选不满足条件时说明并重新问。

## 2. 开工计划（四问拍板后、动手前，一次性用户确认）

1. **依赖分析**：逐票读 ticket 的 `Blocked by`，并核对产出物层面的隐性耦合——共享文件/目录、接口契约（后票消费前票产出的 ViewModel/接口等）、数据库迁移、前后端咬合——形成"票 → 前置"依赖图，标出无依赖、可立即开工的票。
2. **编组并行**：相互无依赖且文件域不重叠的票拆成并行组（硬规则：同一时间只允许一张票产出数据库迁移文件——多票各生成迁移会分叉版本链），每组独立工作树、独立执行类子智能体（组内按问 1/问 2 路由视觉/非视觉任务），共用问 3 的路 A 审核者；有依赖的票排后续梯队，前置票验收合并后解锁。单票或天然串行的轮次退化为一条梯队，同样走本节。
3. **汇报并等确认**：向用户汇报（AskUserQuestion 或文字均可，必须等显式确认）：本轮票清单与分组（谁并行、谁串行、谁等谁）、每组执行者与工作树安排、审查路安排、推进顺序。用户的调整直接采纳、按新计划开工，不二次确认。
4. 确认后按第 3 节开工。这是开工前唯一一次向用户要确认；此后全程自动推进（节奏见第 8 节）。

## 3. 派发前准备（管理员做，主工作区操作）

1. **核票 + 分类扫描**：读 ticket，确认 `Blocked by` 均已 resolved/done、本票与在跑票文件域不重叠（按文件与目录判，不只看依赖边）。逐条判定本票是否产出页面/模板/样式/UI 代码——命中即路由给问 2 的视觉执行者（产出并自验，打包档位按入口视觉路由约定），问 1 的非视觉执行者只承担逻辑/数据层；**"复刻既有形态/断言锁死/无设计空间"不构成豁免理由**——路由按产出物性质判定，不按设计自由度（视觉任务误派非视觉执行者是常见缺陷来源）。
2. **占票**：ticket `Status:` 改 `claimed`。`.scratch/` 下所有票据状态、勾选、Comments 归管理员维护，子智能体一律不碰。
3. **建 QA 文档**：项目根建 `QA/`（首次使用时创建并写入 `.gitignore`），按第 5 节模板建 `QA-<票号>-<slug>.md`，更新索引 `QA/INDEX.md`（每份一行：票号 | 工作树/执行区 | 状态 | 最后更新时间）。
4. **工作树**：任何票必须在独立工作树执行（铁律 4）。默认由子智能体自建；**并行派发多票时由管理员预建各工作树**（串行建、时间戳天然错开），路径与分支写入各自 QA 文档头部，子智能体按给定路径进入。
5. **复制清单**：票需要 gitignore 资产（`.env`、`instance/`、上传目录、本地数据库等）才能运行/测试时，把这些文件列入 QA 文档头部"复制清单"（源路径 → 工作树内路径）。子智能体建树后按清单从主工作区复制进树：仅本地磁盘两目录间复制，不外发、不 `git add`/提交、内容不进代码/QA 文档/汇报正文。主工作区对这些文件始终只读；清单同时是第 8 节收尾删除副本的依据。
6. **路 C 前置自检**（每轮一次）：按 defaults.md 登记的机器初审提供者命令跑连通性自检（带新生成会话标识），并确认输出语言为中文。未登记时先完成提供者接入（examples/ 有官方范例）或经用户决定本轮免路 C；自检不可用时向用户说明，由用户决定本轮免路 C 还是先修复。

## 4. 派发：非阻塞派发＋提示词规范

**一律非阻塞派发**：执行者与审查子智能体（路 A/路 B，含复合复核的两个实例）全部以非阻塞方式（`run_in_background: true`）派出，管理员不挂起等待——运行期间轮询任务输出与各票 QA 文档，并行推进纪律核对等自身工作；需要答复或唤醒时向对应子智能体发消息（SendMessage 类机制或等效方式）。第 5 节 QA 轮转与第 9 节心跳超时处置均以此为前提。

提示词简单明了，只讲五件事，不讲实现细节：

1. **用什么方法**：实现流程优先用环境已装的 implement 类技能、工作树流程优先用 worktree 类技能（子智能体无法经 Skill 工具触发时自行读取其 SKILL.md 等效遵循;提示词给出技能文件路径即可）；环境未装时，按本包 appendix/engineering.md（工程纪律基线）与 appendix/worktree.md（工作树操作规范）执行。
2. **做哪票**：ticket 文件绝对路径（必要时附 spec 路径）。实现方案让子智能体自己研究 ticket、spec、既有代码与项目规则（AGENTS.md、.rules/）。
3. **QA 文档绝对路径**：遇阻写文档并停机（第 5 节）。
4. **执行者身份与视觉自验**：写明身份是视觉/非视觉执行者（混合拆分包分别写明各自文件域边界）；视觉执行者的交付汇报必须附**截图证据**（每项预期 通过/不通过 ＋ 图中可见证据）。
5. **四条行为纪律（内联）**：
   - 全量回归禁令：不自主运行全量测试套件，只跑与票直接相关的测试（此条覆盖 implement 类技能"最后跑完整套件"的要求,若该技能有此要求）；
   - 只读边界：不碰 `.scratch/`、不碰主工作区；一切修改限工作树内、提交只打工作树分支；对主工作区仅允许只读，外加按复制清单把所需未跟踪文件复制进树这一个例外动作；
   - 敏感纪律：凭证/token/key 只按约定路径读取使用，内容绝不进代码、文档、汇报；
   - QA 纪律：遇阻写 QA 文档并停机；每个里程碑（读完关键材料/完成一个模块/跑完一组测试）更新 QA 文档状态行。

基调示范："完成 ticket XX（你的身份是 <视觉/非视觉执行者>）,实现流程与工作树流程按 <已装技能路径 或 appendix/ 两份基线文档> 执行；QA 文档在 <绝对路径>，遇阻写入并停机；边界纪律见下。……实现方案自行研究。"

## 5. QA 文档轮转

模板（管理员派发前建好骨架）：

```markdown
# QA-<票号>-<slug>

- 票号：<NN-slug> ｜ 执行者：<类型> ｜ 路A：<类型> ｜ 路B：<类型> ｜ 路C：机器初审（<提供者>）
- 工作树：<WT_PATH> ｜ 分支：<WT_BRANCH>
- 复制清单（源路径 → 工作树内路径；收尾删除依据）：<无 / 逐行列出>
- 状态：running ｜ 最后更新：<时间>

## Round N — <时间> — <管理员/执行者>
<问题或答复正文>

## 当前待决
<无 / 待管理员答复的问题>
```

状态机：`running` →（遇阻）`waiting-main` →（答复工返）`running` →（交付，进审查）→（审核退回）`rework` →（返工再交付，重走审查）→ …… → `done` / `failed`。

轮转流程：

1. 执行者遇阻 → 在 QA 文档追加 Round 条目、状态改 `waiting-main`、停机，最终消息只说"问题已写入 QA 文档，等待答复"。
2. 管理员读 QA 文档 → 能代答的直接把答复写入（状态改回 `running`）；需用户决策的在主对话问用户，答案以管理员名义写入文档。
3. 管理员唤醒执行者，消息仅一句："答复已写入 QA 文档，继续工作"。
4. 完成/失败：执行者把最终结论写入 QA 文档（`done` / `failed`），并向管理员交最终汇报。

**审查报告区块**：路 A、路 B 审查者各自只允许在文档末尾追加自己的报告区块——路 A `## 路A审核报告 — 第 N 轮`、路 B `## 路B复核报告 — 第 N 轮`（每轮一个），文档其余部分对它们只读（铁律 3）。两路互不知晓对方结论（独立性的组成部分）。路 C 不是子智能体、无写入权——其报告由管理员转录为 `## 路C机器初审报告 — 第 N 轮` 区块。

**禁令**：QA 文档中不得出现凭证、token、key、`.env` 内容。

## 6. 执行侧职责（视觉/非视觉通用）

- 按 **implement 类技能**（或 appendix/engineering.md 工程纪律基线）完整执行：实现票内工作、在既定 seams 上测试、定期跑直接相关测试、交付前**先自行做一遍代码自查并修复问题**（环境有 code-review 类技能则用之）——各审查路与管理员验收不替代这一步。
- 按 **worktree 类技能**（或 appendix/worktree.md 工作树操作规范）完整执行工作树流程：建树、按复制清单复制未跟踪文件（复制件不提交）、树内开发与提交（提交前缀遵循项目规则）、自验、报告改动清单/提交清单/测试结果。
- 项目规则（AGENTS.md、.rules/）与项目测试纪律照常适用。
- **视觉执行者额外**：按闭环工作法自验（读图/截图 → 核对预期 → 定位差距 → 修改 → 再截图 → 再核对），交付汇报附每项预期的 通过/不通过 与图中可见证据。

## 7. 验收：三路审查 + 管理员终裁

执行者交付（QA 状态 `done` ＋ 最终汇报）后：管理员**非阻塞并行派出路 A、路 B 审查子智能体**（路 B 为复合复核时按第 2 条派两个；各路互不知晓对方结论），**同时后台启动路 C 机器初审**，并亲自完成纪律与结构核对。

**两路（A/B）提示词必须一致**（信息差或要求差会让两路发现面不对等，双审失效）：同材料清单、同审查要求、同纪律、同输出格式，仅角色标识与 QA 报告区块名不同——落笔时先写好一份中立模板再复制改角色段，禁止给任一路增删要求；视觉/非视觉任务拆分时，两路的综合要求合并后必须等同。材料只给客观事实——ticket 路径、spec 路径、工作树路径与分支、改动文件清单、测试输出、QA 文档路径——**不得包含管理员自己的预判、倾向或已发现的问题**（防锚定）。**不得以亲自读 diff/复跑测试替代两路派出**（铁律 5）。

1. **路 A · 异构审核**（问 3 拍板）。纪律：**只读边界**（对工作树与主工作区只读，可运行只读命令与直接相关测试做复核，不修改任何源代码与票据，修复不归它管）、**落盘**（结论写入该票 QA 的路 A 区块，并向管理员交同样的最终汇报）、**分级输出**——**阻塞**（必须返工）/ **建议**（可放行但记录在案）/ **通过**，每条附证据（文件行号、测试输出；**视觉票必须亲自看图**，写明截图位置与预期差异）。
2. **路 B · 独立复核**。两种运行形态：执行者模型**多模态**时＝单一复核子智能体（执行者模型的独立会话实例：全新会话、未参与实现、只拿材料——独立立场不因与执行者同模型而丧失），独自完成下述全部复核内容；执行者模型**非多模态**时＝**复合复核**，管理员并行派两个——① 执行者模型的独立会话实例，承担下述复核内容的全部非视觉部分（四要素核对/抽查核实/行为预期/断言全集/构造性验证）；② 问 4 拍板的视觉审核子智能体，只看图核验视觉预期（写明截图位置与预期差异）。整合方式：主体实例把非视觉结论写入路 B 区块，视觉结论由管理员转录并入同一区块（同路 C 转录模式），合成一份完整的路 B 报告——**视觉审核子智能体只占路 B 的视觉维度，不接管路 B 整体**。纪律与路 A 相同（防锚定/只读边界/落盘/分级输出）。复核内容：
   - 四要素核对：改动文件清单、提交清单（`git log 主分支..工作树分支 --oneline`）、测试结果（哪些通过、哪些没跑及原因）、QA 遗留问题清零；
   - 抽查核实：亲自读关键 diff；亲自跑直接相关测试（不自主全量回归，需要全量时建议、由用户决定）；
   - 行为预期核对：按 ticket 勾选项逐条验收；涉及新功能行为预期的，确认已配测试锁定；
   - 断言全集核对：改动涉及共享标识（表结构/表头文案、注册表/枚举集合、与既有标识同前缀的新键名）时，`grep -rn "<被改标识>" project_files/tests/` 列出断言全集，逐条三选一显式处理——已同步 / 语义不变显式豁免 / 守卫已改单词边界防子串误伤；未做的退回补齐（常见事故形态三例：表头文案、注册集合、前缀键子串误伤）；
   - **构造性验证下限**：每轮必须构造至少一个执行者测试未覆盖的新形态探针或负向对照（形态参照：移除/还原修复代码的对拍、并发或边界注入、跨实例重建的多步用户序列、跨模块交叉场景），并给出修复前后行为对比——复跑执行者测试全绿只是门槛，不是通过结论；无构造性验证的报告退回重做。
3. **路 C · 机器初审**（可插拔提供者,管理员亲自运行,非子智能体）：独立进程＋独立凭证审工作树 diff，与所有子智能体零共享上下文——不吃派发材料、不知晓 A/B 结论，防锚定天然成立。
   - **提供者接口约定**：输入＝分支 diff（主分支 → 工作树分支）;输出＝分级缺陷清单（critical/high/medium/low,行级定位）;运行要求＝独立进程、独立 LLM 端点/凭证、会话标识每次**新生成**且不得复用。提供者命令从 defaults.md 的机器初审段带出;未登记时先探测本机可用审查 CLI,探测不到则询问用户接入（接入范例见 examples/provider-opencode-review.md）或本轮免跑;
   - 输出语言：中文；仍输出英文则补设提供者配置后重跑；
   - 时序：与路 A/路 B 派发同时后台启动，管理员趁其运行完成纪律核对；后台超 20 分钟无产出视为超时，按第 9 节处置；可向提供者附业务背景参数（仅中立事实、取自 ticket 原文）；
   - 职责边界：只产出代码缺陷发现（bug/安全/性能/风格，行级定位）。行为预期核对、断言全集核对、构造性验证、视觉验收不在其覆盖内，仍由路 A/路 B/管理员硬性承担——路 C 通过不替代任何一路；
   - 结果处理：按 severity 归并——critical/high 列为候选阻塞逐条核实，medium 列为候选建议，low 默认忽略（low 档噪音多）；其行号可作两路报告行号存疑时的参照基准。摘录（命令、会话标识、提供者、分级问题清单）由管理员转录进 QA 的路 C 区块，完整输出留档 QA 目录；
   - 范围与泄漏面：只审工作树分支相对主分支的已提交 diff——复制清单的未跟踪文件（`.env` 等）天然不在其视野；
   - 豁免：改动不含代码文件（仅文档/纯注释类）的票免跑，QA 文档记豁免原因。
4. **管理员纪律与结构核对**（亲自完成，不可委托）：
   - diff 范围核对：改动文件与票面范围一致，无范围外夹带；
   - 边界核对：主工作区无越权写入（执行者/审查者一律只读主工作区，复制清单是唯一例外）、无临时文件/联接残留等现场污染；
   - 敏感核对：凭据/密钥零泄漏（对 diff 与产出物逐命中甄别，区分删除行与新增行）；
   - 台账核对：票据勾选与 Status、QA 文档状态行、提交清单三者一致。
5. **综合裁决（不可让渡）**：读三路报告＋纪律核对结果，逐条归并成最终问题清单；结论冲突时显式裁定并把裁定与理由写入 QA Round；可依纪律核对与客观材料对任一路的定级做升/降级（附证据）。存在阻塞级问题 → 按第 9 节退回返工或重派；全部通过 → 进第 8 节合并。
6. **返工后重验**：退回返工的票修复再交付后，路 A/路 B 全部重跑＋路 C 重新运行——不因"只改了一点"只重跑一路。

## 8. 合并与收尾（管理员做）

1. **验收通过即合并**：不向用户请示合并授权、不中途询问，整轮任务自动推进直到所有票终态（开工确认是全程唯一一次用户确认，见第 2 节）；单票收尾后直接接续下一票派发，仅必须用户决策的阻塞（合并冲突文件清单、审查子智能体不可用等）才停下问用户。
2. 在主工作区逐票串行合并：优先 `--ff-only`，不能快进则 `--no-ff`；冲突不自行解决，列冲突文件清单交用户。
3. 清理现场（按 appendix/worktree.md 收尾规范）：先按复制清单逐项删除工作树内全部副本（不先清理 `git worktree remove` 会因"不干净"失败，且敏感内容必须随树清除、不得残留），再 `git worktree remove`、检查并清理分支 upstream 后删分支、`git worktree prune`。
4. 票据与档案：ticket 勾选验收项、`Status:` 置 done/resolved；QA 文档的结论性内容（关键决策、遗留问题、**三路验收结论与冲突裁定**）摘录进 ticket 的 `## Comments`（进 git 留档）；QA 状态置 `done` 并更新 `QA/INDEX.md`。
5. **最终汇总**：所有票均到达终态（done / failed）后统一汇报——各票改了什么、跑了哪些测试、验收情况（A/B/C 各路结论、冲突裁定、路 C 降级/豁免情况、返工轮次）、合并与清理结果、失败与重派情况、是否建议全量回归。

## 9. 失败处置

- **审查路 A/路 B 不可用**（含路 B 的视觉审核子智能体）：长时间无响应或不可用时，停下向用户说明并推荐替代模型（替代者须满足该路的模型与多模态条件），用户拍板后继续——独立审查是硬规则，不得静默降级为单路审查放行。任一路发现阻塞级问题：管理员裁定确认后在 QA 记 Round、状态改 `rework`、唤醒执行者返工，重派流程同下。
- **路 C 失败/超时**（与 A/B 处置不对称，勿混淆）：命令失败、超时或 LLM 端点不可用时**可降级跳过继续验收**——路 A＋路 B＋管理员核对已满足双审硬规则——但必须在 QA 文档记录原因、最终汇总向用户报告；**同一轮连续 2 票路 C 失败则停下**，用新会话标识重跑提供者连通性自检,检查命令与凭证配置（多为额度/网络问题），修复或经用户确认本轮免路 C 后再继续。路 A/路 B 不可用仍按硬规则处置，不因路 C 存在而放宽。
- **执行者心跳超时**（建议上限 10 分钟）：先读其 QA 文档看最后状态——状态新鲜则继续等；停滞则唤醒询问；唤醒无响应则带 QA 现场**缩小任务重派**（新子智能体读同一 QA 文档接前情）。
- **失败不甩锅**：子智能体失败或验收不通过，管理员在 QA 文档记录原因与重派决定并继续推进（不问用户是否继续），失败情况留到最终汇总如实汇报；不以"代码已写完"判定完成。
