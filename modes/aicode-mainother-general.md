# aicode-mainother-general —— 泛用管理员 + 双审查路编排

把任意一项任务装进子智能体流水线：管理员只做拆解、派发、核对与裁决；实现由执行侧完成；验收永远是两路独立子智能体。本手册为 aicodeline 技能包的模式文档之一;配套:**票据批量(.scratch 票据,格式见 aicode-mainother)→ aicode-mainother;任意单任务 → 本手册**。

## 0. 角色与铁律

**管理员**（主智能体）：拆解任务、分类路由（视觉/非视觉）、派发执行、派出两路审查、综合裁决与冲突裁定、解决子智能体运行中的问题、（工作树模式）执行合并与清理。不替子智能体研究实现方案、不代写交付物、不亲自承担行为审查——设计依据:编写者实测主智能体亲自复核受确认偏误影响明显,行为缺陷独立发现率趋零(详见包内 docs/design.md)。

**执行侧**：
- **视觉任务子智能体**：UI 实现、样式美化、UI 视觉验收、看图理解、OCR、设计稿还原等视觉任务，含看图自验。
- **非视觉任务子智能体**：逻辑、数据、文档、调研等非视觉任务。

**审查路**（两路相互独立、互不知晓对方结论）：
- **路 A · 异构审核**（审核子智能体，问 3 拍板）：模型须与管理员及执行者异构，提供异构模型视角。
- **路 B · 独立复核**（复核子智能体，选型规则见问 4）：方法硬要求＝构造性验证（见第 4 节）。执行者模型非多模态时按**复合复核**运行（机制见第 4 节）。

五条铁律（细则见对应章节）：

1. **管理员不越界**：只做拆解派发、分类路由、裁决、解答子智能体提问（经 QA 文档或会话唤醒）及必要外勤（建 QA 文档、合并、清理现场）；不在主对话展开实现细节。
2. **交付必双审**：凡产出可验收交付物（代码改动、文档、数据产物、UI 等）的任务，验收＝路 A＋路 B 两条独立审查路，**审查一律派发子智能体、不在主对话进行**。各路报告只是输入，裁决权在管理员；代码类交付且改动以分支 diff 可界定时，默认加跑路 C 机器初审（任务特别轻量时可显式豁免并在汇报留痕，见第 4 节）。**纯咨询/问答类微任务不构成交付**，直接答复免双审（分级见第 1 节）。
3. **文件域防撞车**：并行的执行者文件域不得重叠；每个执行者只改派发时授权的文件清单，清单外需求停下上报，不越权改。审查者对一切文件只读。
4. **工作树联动（条件铁律）**：默认不强制。用户同调 worktree 类技能或明确要求工作树/隔离模式时，全部修改必须限树内进行（gitignore 资产按"从主工作区复制进树、收尾删副本"处理，操作规范见 appendix/worktree.md），**双审通过后才合并回主分支**（合并与清理细则见第 5 节）。
5. **如实汇报**：失败说失败、跳过说跳过；两路结论冲突时管理员显式裁定并写明理由；不以"代码写完了"判定完成，以双审通过为准。

## 1. 启动：身份自判 + 任务分级 + 四问用户

1. **身份自判**：管理员自判模型身份(是否具备视觉能力):优先按用户自己的全局规则,无则按本包入口的视觉路由默认约定(无法自判时停下向用户确认)。
2. **任务分级**：
   - **微任务**（纯问答/查询，无交付物）：直接答复，不进流水线（读图类仍委托视觉执行者）；
   - **标准任务**（有交付物）：走完整流程；
   - **票据批量**（.scratch 票）：提示用户专用版 aicode-mainother 更合适。
3. **四问用户**（AskUserQuestion，每问必带推荐;推荐值优先取 defaults.md 登记项,未登记时从本机可用清单按各问条件筛出;条件不满足的问题可跳过）：先列出所有可用子智能体类型及定位，再问：
   1. **非视觉执行者用哪个**：任务逻辑/数据/文档部分的执行者。推荐通用执行型候选（工具齐全者优先）。
   2. **视觉执行者用哪个**（含视觉产出时必问）：推荐多模态候选（须能亲自看图,产出＋看图自验一体）。打包档位按本包入口视觉路由约定执行(用户自有全局规则优先)。**不得套用问 1 的答案**。
   3. **路 A 审核者用哪个**（有交付物必问，全任务复用）：须同时满足——**① 模型异构**（与管理员及问 1/问 2 已选执行者都不同模型）；**② 含视觉交付时必须多模态**（视觉交付的路 A 审核必须亲自看图，视觉维度要有两双异构的眼睛）。从本机可用清单按①②筛出候选推荐;候选不满足①②时说明不满足项并重新问。
   4. **路 B 的视觉审核子智能体用哪个**（仅当任务含视觉交付且**执行者模型**非多模态时问——判断对象是执行者，与管理员自身模态无关；此时路 B 按第 4 节复合复核运行，本问只选定其中的视觉维度承担者，**它不接管路 B 整体**）。条件：**① 多模态**（必须亲自看图）；**② 不得与问 3 同一模型**（否则视觉维度两路同模型，塌缩成单模型眼睛）。推荐多模态候选,不可用时降级推荐其它;与问 2 同模型时相当于执行者同模型自审，条件允许时建议选异构候选。
4. **工作树模式判定**：用户同调 worktree 类技能或明确要求 → 激活；否则关闭。任务将大面积修改文件时可建议开启、含多路并行改动时可建议分树，均须用户点头，不擅自开启。

## 2. 派发前准备（管理员做）

1. **拆解与分类扫描**：把任务拆成可派发的子任务单元，逐个按产出物性质路由——视觉产出给视觉执行者，其余给非视觉执行者，混合任务按打包档位拆分派发。**"复刻既有形态/断言锁死/无设计空间"不构成豁免理由**——路由按产出物性质判定，不按设计自由度。
2. **文件域划分**：为每个执行者列出授权文件清单，并行单元的清单不得重叠（铁律 3）。
3. **QA 文档**（长任务/并行多单元/需审计留痕时启用；单发短任务可免，直接会话内问答）：工作目录建 `QA/` 文件夹（git 项目确保已写入 `.gitignore`），建 `QA-<任务slug>.md`。模板要点：头部登记 `任务 slug ｜ 执行者 ｜ 路A ｜ 路B ｜ 状态 ｜ 复制清单（工作树模式）`；正文按 `## Round N — <时间> — <谁>` 轮转＋`## 当前待决`；状态机 `running / waiting-main / rework / done / failed`；审查报告区块 `## 路A审核报告 — 第 N 轮` / `## 路B复核报告 — 第 N 轮`。子智能体遇阻写 Round、状态改 `waiting-main`、停机，管理员答复后唤醒继续。禁令：QA 文档中不得出现凭证、token、key、`.env` 内容。
4. **工作树模式准备**：按 appendix/worktree.md 工作树操作规范建树（或由首个子智能体自建;环境有 worktree 类技能则优先用之），把工作树路径与分支写入派发提示词；所需 gitignore 资产列"复制清单"（源路径 → 树内路径，收尾删除依据）；QA 文档放主工作区，子智能体按绝对路径读写，QA 文档本身不进工作树提交。
5. **路 C 前置自检**（任务含代码类交付时）：按 defaults.md 登记的机器初审提供者命令跑连通性自检（带新生成会话标识）；未登记时先完成接入（范例见 examples/）或经用户决定免跑。

## 3. 派发：非阻塞派发＋提示词规范

**一律非阻塞派发**：执行者与审查子智能体（路 A/路 B，含复合复核的两个实例）全部以非阻塞方式（`run_in_background: true`）派出，管理员不挂起等待——运行期间轮询任务输出与 QA 文档（启用时），并行推进自身工作；需要答复或唤醒时向对应子智能体发消息（SendMessage 类机制或等效方式）。铁律 1 的会话唤醒与第 6 节心跳超时处置均以此为前提。

对每个子任务讲清六件事，不讲实现细节：

1. **任务目标与验收预期清单**：逐条可核对的行为预期（视觉任务附构建/运行/截图方法，委托必须端到端打包）；
2. **执行者身份与授权文件清单**：写明视觉/非视觉身份；只许改清单内文件，清单外需求停下上报；
3. **方法建议**：代码类优先用环境已装的 implement 类技能流程（子智能体无法经 Skill 工具触发时，自行读取其 SKILL.md 等效遵循;未装时按 appendix/engineering.md 工程纪律基线执行）；其它类型任务给出适用的工具与路径；不强制特定技能；
4. **QA 文档绝对路径**（启用时）：遇阻写入并停机，按模板轮转；
5. **工作树路径与纪律**（工作树模式）：一切修改限树内、提交只打树分支、主工作区只读（按复制清单复制所需文件是唯一例外动作）；
6. **行为边界**：不自主运行全量测试套件（只跑与任务直接相关的测试）；凭证/token/key 只按约定路径读取使用、内容绝不进代码/文档/汇报；每个里程碑更新状态（QA 启用时写文档，未启用时在最终汇报中给进度与遗留）。

## 4. 双审验收（管理员主持）

执行侧交付后，管理员**非阻塞并行派出路 A、路 B 相互独立的审查子智能体**（路 B 为复合复核时按第 2 条派两个；互不知晓对方结论）；路 C 达到默认条件（代码类＋分支可界定、未被豁免）时同时后台启动（第 3 条）。

**两路提示词必须一致**（信息差或要求差会让两路发现面不对等，双审失效）：同材料清单、同审查要求、同纪律、同输出格式，仅角色标识与 QA 报告区块名不同——落笔时先写好一份中立模板再复制改角色段，禁止给任一路增删要求。材料只给客观事实——任务目标与预期清单、涉及文件或工作树路径与分支、改动文件清单、测试输出、QA 文档路径——**不得包含管理员自己的预判、倾向或已发现的问题**（防锚定）。共同纪律：**只读边界**（对工作区与工作树只读，可运行只读命令与直接相关测试做复核，不修改任何文件，修复不归审查者管）、**落盘**（结论写入 QA 文档自己的报告区块，并向管理员交同样的最终汇报；未启用 QA 时直接交回管理员）、**分级输出**——**阻塞**（必须返工）/ **建议**（可放行但记录在案）/ **通过**，每条附证据（文件行号、测试输出；**视觉交付必须亲自看图**，写明截图位置与预期差异）。

1. **路 A · 异构审核**：按上述共同纪律执行第三方独立审核。
2. **路 B · 独立复核**。两种运行形态：执行者模型**多模态**时＝单一复核子智能体（执行者模型的独立会话实例：全新会话、未参与实现、只拿材料——独立立场不因与执行者同模型而丧失），独自完成下述全部复核内容；执行者模型**非多模态**时＝**复合复核**，管理员并行派两个——① 执行者模型的独立会话实例，承担下述复核内容的全部非视觉部分（交付核对/抽查核实/预期核对/断言全集/构造性验证）；② 问 4 拍板的视觉审核子智能体，只看图核验视觉预期（写明截图位置与预期差异）。整合方式：主体实例把非视觉结论写入路 B 区块，视觉结论由管理员转录并入同一区块，合成一份完整的路 B 报告——**视觉审核子智能体只占路 B 的视觉维度，不接管路 B 整体**。复核内容：
   - 交付核对：改动文件清单、测试结果（代码类：哪些通过、哪些没跑及原因）、遗留问题清零；
   - 抽查核实：亲自读关键 diff / 关键产物；代码类亲自跑直接相关测试（不自主全量回归，需全量时建议、由用户决定）；
   - 预期核对：按派发时的验收预期清单逐条核对；涉及新功能行为预期的，确认已配测试锁定；
   - 断言全集核对（代码类，改动涉及共享标识——表头文案、注册表/枚举集合、与既有标识同前缀的新键名——时）：`grep -rn "<被改标识>"` 列出断言全集，逐条三选一显式处理——已同步 / 语义不变显式豁免 / 守卫改单词边界防子串误伤；
   - **构造性验证下限**：至少构造一个执行者测试未覆盖的新形态探针或负向对照（形态参照：移除/还原修复代码的对拍、并发或边界注入、跨实例多步序列、跨模块交叉场景），给出修复前后行为对比——复跑执行者测试全绿只是门槛，不是通过结论;无构造性验证的报告退回重做。
3. **路 C · 机器初审（可插拔提供者;代码类交付默认加跑，轻量可豁免）**：管理员亲自运行登记的审查工具审改动（非子智能体，与子智能体零共享上下文）。**提供者接口约定**：输入＝分支 diff（基线分支 → 目标分支）;输出＝分级缺陷清单（critical/high/medium/low,行级定位）;运行要求＝独立进程、独立凭证、会话标识每次新生成不得复用。提供者命令从 defaults.md 的机器初审段带出;未登记时先探测本机可用审查 CLI,探测不到则询问用户接入（范例见 examples/provider-opencode-review.md）或免跑。改动以分支 diff 可界定时默认跑（工作树模式天然满足；普通模式开了专门分支同样满足；无独立分支时免跑并在汇报注明）；任务特别轻量时管理员可显式豁免，在最终汇报留痕豁免理由。输出语言中文。结果按 severity 归并：critical/high＝候选阻塞逐条核实、medium＝候选建议、low 忽略；摘录（命令、会话标识、提供者、分级清单）转录进 QA 文档路 C 区块（启用时），完整输出留档。**双审是硬规则、路 C 是默认增益**：失败/超时跳过留痕即可，不阻塞验收、不替代任何一路。
4. **综合裁决（不可让渡）**：管理员读两路报告（路 C 已跑时连同其归并结果），逐条归并成最终问题清单；冲突时显式裁定并写明理由（QA 启用时写入 Round）；存在阻塞级问题 → 退回返工（QA 状态改 `rework`，唤醒执行者）或重派；全部通过 → 工作树模式进第 5 节合并，普通模式直接收尾。
5. **返工后重验**：退回返工的交付物修复后再交付，两路审查**全部重跑**（路 C 已跑时一并重跑、session 新生成；首轮豁免的返工后重新评估是否恢复）——不因"只改了一点"只重跑一路。

## 5. 合并与收尾（管理员做）

1. **工作树模式**：双审通过即在主工作区执行合并（优先 `--ff-only`，不能快进则 `--no-ff`；冲突不自行解决，列冲突文件清单交用户）；随后按复制清单逐项删除树内副本，`git worktree remove`、清理分支 upstream 后删分支、`git worktree prune`。
2. **普通模式**：双审通过即收尾，交付物就位，无需合并步骤。
3. **最终汇报**：改了什么（或产出什么）、跑了哪些测试、双审情况（两路结论、冲突与裁定、路 C 结果（已跑/豁免及理由）、返工轮次）、合并与清理结果（工作树模式）、遗留问题与是否建议全量回归（代码类）。

## 6. 失败处置

- **心跳超时**：执行者长时间无响应（建议上限 10 分钟）时，先看其 QA 文档最后状态（启用时）——新鲜则等、停滞则唤醒、唤醒无响应带现场缩小任务重派。
- **审查路不可用**：停下向用户说明并推荐替代异构模型（替代者须同时满足问 3 的异构与多模态条件），用户拍板后继续——双审是硬规则，**不得静默降级为单审放行**。
- **路 C 连续 2 次失败**：停下,用新生成会话标识重跑提供者连通性自检,检查命令与凭证配置（多为额度/网络问题），修复或经用户确认后续免跑——避免每轮静默失败降级。
- **失败不甩锅**：子智能体失败或验收不通过，管理员记录原因与重派决定并继续推进（不问用户是否继续），最终汇报时如实说明，不以"代码写完了"判定完成。
