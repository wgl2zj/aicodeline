# aicode-mainother-general-workflow —— 泛用单任务 · 工作流引擎版(试点)

把任意一项任务装进工作流 run。与原版 aicode-mainother-general 的分工只在一处:**执行引擎**——原版由管理员在主会话非阻塞派发子智能体(QA 文档轮转、心跳盯梢);本版由一个后台 run 自动驱动"执行+双审",管理员在 run 边界外终裁(两段式)。角色定义、双审设计、任务书纪律与原版同源,以本技能为准的差异见第 7 节。

## 0. 定位、分工与试点纪律

- **同源分工**:aicode-mainother-general(子智能体派发,成熟)= 默认;本技能(工作流引擎,试点)= 用户点名或明确要后台自动推进/失败保底/逐项打点时;票据批量(.scratch 票)→ aicode-mainother(-workflow);统一入口 aicodeline。
- **试点纪律(首次使用必须执行)**:先用 1 个小型标准任务(建议非视觉、单元数 1、含一个代码类交付单元)试跑一个 run,验证四件事——①模型名册各就各位;②路 C 适配在本机真实可用(试点任务含代码类交付时,第 3 节);③escalation 通路顺畅;④run 结束返回材料与验收报告完整。四项全过再上常规任务。
- 试点期内本技能与原版并存;用户未点名引擎、也未提出上述需求(后台自动推进/失败保底/逐项打点)时,不主动选用本技能。

## 1. 角色与铁律(两段式)

**第一段(run 内,脚本机械驱动)**:逐单元派发执行者 → 交付后并行派出路 A、路 B 审查 agent(代码类且分支可界定时默认后台跑机器闸门)→ 机械聚合 → 打点汇报;返工循环带轮次上限。

**第二段(run 外,管理员=主智能体)**:启动前外勤(分级、拆解、四问、写名册与脚本、确认启动)+ run 期间应答 escalation + run 结束后终裁、(工作树模式)合并、收尾、最终汇报。

**执行侧**(run 内 agent,按单元路由):视觉任务执行者(UI 实现、样式美化、看图理解、OCR、设计稿还原等,含看图自验)/非视觉任务执行者(逻辑、数据、文档、调研等)。

**审查路**(两路相互独立、互不知晓对方结论):
- **路 A · 异构审核**(C 题模型):模型须与管理员及执行者异构;含视觉交付时须多模态亲自看图。
- **路 B · 独立复核**(执行者模型的独立会话):方法硬要求=构造性验证(见第 3 节任务书)。执行者模型非多模态时为**复合复核**——非视觉维度由执行者模型独立会话承担,视觉维度由 D 题模型看图,两份结论由脚本整合为一份路 B 材料;视觉维度 agent 不接管路 B 整体。

五条铁律(与原版同源,两段式翻译):

1. **管理员不越界**:run 内由脚本机械驱动,管理员的 run 内职责仅限应答 escalation 与必要的运行性处置(停滞重开/方向修正/停止处理)——不做冲突裁定、不做升降级、不执行合并;其余职责为外勤、终裁、(树模式)合并、收尾、最终汇报等;不替子智能体研究实现方案、不代写交付物、不亲自承担行为审查(设计依据:编写者实测主智能体亲自复核受确认偏误影响明显,行为缺陷独立发现率趋零,详见包内 docs/design.md)。
2. **交付必双审**:凡产出可验收交付物(代码改动、文档、数据产物、UI 等)的任务,验收=路 A+路 B 两条独立审查路,审查一律 run 内派出、不在主对话进行;各路报告只是输入,裁决权在管理员。代码类交付且改动以分支 diff 可界定时,默认加跑路 C 机器闸门(任务特别轻量时可显式豁免并留痕,第 3 节)。**纯咨询/问答类微任务不构成交付**,不进 run 直接答复(分级见第 2 节)。
3. **文件域防撞车**:并行执行单元的文件域不得重叠;每个执行者只改任务书授权的文件清单,清单外需求经 escalation 上报,不越权改;审查者对一切文件只读。
4. **工作树联动(条件铁律)**:默认不强制。用户同调 worktree 类技能或明确要求工作树/隔离模式时,全部修改限树内(gitignore 资产按"复制进树、收尾删副本"处理,操作规范见 appendix/worktree.md),**双审通过且管理员终裁后合并回主分支**(第 5 节)。任务将大面积修改文件时可建议开启、多路并行改动时可建议分树,均须用户点头。
5. **如实汇报**:失败说失败、跳过说跳过;两路结论冲突时管理员显式裁定并写明理由;不以"代码写完了"判定完成,以双审+终裁为准。run 内"通过"仅为**候选放行**(管理员可否决);冲突或轮次用尽标记**待裁定**交回。

## 2. 启动:身份自判 + 任务分级 + 五问 + 外勤

1. **身份自判**:管理员自判模型身份(是否具备视觉能力):优先按用户自己的全局规则,无则按本包入口的视觉路由默认约定(无法自判时停下向用户确认)。
2. **任务分级**:**微任务**(纯问答/查询、无交付物)直接答复,不进 run(读图类仍委托多模态通道);**标准任务**(有交付物)走完整流程;**票据批量**(.scratch 票)提示用户 aicode-mainother(-workflow) 更合适。
3. **五问(纯文字问答,禁用 AskUserQuestion——本机模型配置多,提问工具选项数不够)**:提问前先经 ListModels 列出本机已配置的**全部模型**,排成带数字序号的清单(推荐项标注"推荐":优先 defaults.md 登记项,未登记时按各题条件筛出);问题排成带**大写字母序号**的问题清单,与模型清单一并列出,请用户以文字回答(如"B3"=B 题选 3 号模型;多题可一并作答,如"A2 C5 E默认"):

   - **A · 非视觉执行者模型**:任务逻辑/数据/文档部分的执行者;推荐可用强模型。
   - **B · 视觉执行者模型**(含视觉产出时必问):须多模态(须能亲自看图,产出+看图自验一体)。不得套用 A 题答案;视觉子任务打包档位按本包入口视觉路由约定执行(用户自有全局规则优先)。
   - **C · 路 A 审核者模型**(有交付物必问,全任务复用):须同时满足——①**模型异构**(与管理员及 A/B 题已选执行者都不同模型);②**含视觉交付时必须多模态**。候选不满足时说明不满足项并重新问。
   - **D · 路 B 视觉维度模型**(仅当任务含视觉交付且**执行者模型**非多模态时问):须①多模态;②不得与 C 题同一模型。与 B 题同模型时相当于执行者同模型自审,条件允许时建议选异构候选。
   - **E · 思考强度**:各角色默认使用所选模型支持的**最高思考强度档**(通常为 max;按各模型 reasoningLevels 而定),是否更改?(更改则指明角色与档位,如"C 用 medium";不答或答"默认"即全部最高档)

   五问答案写入脚本**模型名册**(第 3 节;模型 id 可附 `$<档位>` 后缀指定思考强度),**启动后锁定**;中途换模型=改脚本重发(AmendWorkflow,已完成步骤缓存回放)。
4. **外勤(管理员做)**:拆解任务为可派发子任务单元,逐单元按产出物性质路由视觉/非视觉("复刻既有形态/断言锁死/无设计空间"不构成豁免理由);为每个单元列授权文件清单(并行单元不重叠);工作树模式判定(用户同调或明示才激活;激活时建树、列复制清单);任务含代码类交付时做路 C 前置自检(按 defaults.md 登记的机器初审提供者命令跑连通性自检,带新生成会话标识;未登记时先完成接入——范例见 examples/,或用户决定免跑)。
5. **写脚本并启动**:按第 3 节规范实例化,CreateWorkflow 提交;**确认框=开工计划一次性确认**(阶段图、命令集、脚本全文)。确认后 run 自动推进,不再请示(阻塞类例外见第 6 节)。

## 3. 工作流脚本规范

**模型名册与单元清单(骨架)**:

```ts
// 模型名册:五问答案(A-E;推荐值优先取 defaults.md);启动锁定。ids 来自 ListModels,
// 可附 $<档位> 指定思考强度(E 题答案;默认最高档,如 $max)。
const MODELS = {
  executor: model("<A:非视觉执行者,可带$level>"),
  visual: model("<B:视觉执行者,含视觉交付时>"),
  auditor: model("<C:路A,异构>"),
  bVisual: model("<D:路B视觉维度,条件启用>"),
};
// 拆解结果(管理员外勤时核定):{ id, 目标+验收预期清单, 授权文件清单, visual, 工作树? }
const UNITS = [/* … */];
```

**阶段图(用户在确认框看到的开工计划)**:

```ts
phase("派出各单元执行者");
phase("逐单元执行,交付后双审与机械聚合");   // fan-out 内不再标 phase
phase("汇总验收材料交管理员终裁");          // artifact.markdown 发布 + return
```

**每单元流水线(fan-out 内)**:返工循环**轮次上限 3**;每轮——执行者交付(类型化结果:改动/产物清单、测试结果、截图证据路径、遗留问题)→ `Promise.all` 并行派路 A、路 B(互不知晓;路 B 复合复核时拆两路)→ 路 C 达到默认条件(代码类+分支可界定、未被豁免)时后台跑机器闸门 → 机械聚合:

- 任一路**阻塞**级 → 聚合阻塞清单作为 feedback,返工重走双审(全部重跑);
- 全部"通过/建议" → **候选放行**,跳出循环;
- 轮次用尽 → **待裁定**交回。

每轮 `report()` 打点到看板(单元、轮次、两路结论摘要),失败保底。

**执行者任务书**(六件事,不讲实现细节):①任务目标与逐条验收预期清单(视觉任务附构建/运行/截图方法,端到端打包);②执行者身份与授权文件清单(清单外需求 escalation 上报);③方法建议(代码类优先用环境已装的 implement 类技能流程,给 SKILL.md 绝对路径自行读取等效遵循;未装时按 appendix/engineering.md 工程纪律基线执行;不强制特定技能);④工作树路径与纪律(树模式:修改限树内、提交只打树分支、主工作区只读、复制清单是唯一例外);⑤视觉自验(视觉执行者交付附每项预期通过/不通过+截图证据路径);⑥行为边界——不自主运行全量测试套件(只跑直接相关测试)、凭证只按约定路径读取内容不外泄、**遇阻经 escalation 直问管理员,不再写文档停机**。

**审查任务书(路 A/路 B 必须一致)**:同材料清单、同审查要求、同纪律、同输出格式,仅角色标识不同——先写一份中立模板再复制改角色段。材料只给客观事实——任务目标与预期清单、涉及文件或工作树路径与分支、改动文件清单、测试输出、截图证据路径——**不得包含管理员预判**(防锚定)。共同纪律:只读边界(可运行只读命令与直接相关测试复核,不修改任何文件,修复不归审查者管)、分级输出(**阻塞/建议/通过**,每条附证据;视觉交付必须亲自看图,写明截图位置与预期差异)、遇阻 escalation;审查结论以类型化结果交回脚本,汇总进返回材料与验收报告(替代原版 QA 区块落盘)。路 B 复核内容五项:①交付核对——改动/产物清单、测试结果(哪些通过、哪些没跑及原因)、遗留问题清零;②抽查核实——亲自读关键 diff/关键产物,亲自跑直接相关测试(不自主全量回归);③预期核对——按派发预期清单逐条核对,新功能行为预期确认已配测试锁定;④断言全集核对——代码类改动涉及共享标识(表头文案、注册表/枚举集合、与既有标识同前缀的新键名)时,`grep -rn "<被改标识>"` 列出断言全集,逐条三选一显式处理:已同步 / 语义不变显式豁免 / 守卫已改单词边界防子串误伤,未做的退回补齐;⑤**构造性验证下限**——每轮至少构造一个执行者测试未覆盖的新形态探针或负向对照(形态参照:移除/还原修复代码的对拍、并发或边界注入、跨实例多步序列、跨模块交叉场景),给出修复前后行为对比;复跑执行者测试全绿只是门槛,不是通过结论;无构造性验证的报告退回重做。

**路 C 机器闸门(可插拔提供者;代码类交付且分支 diff 可界定时默认加跑——工作树模式天然满足,普通模式开了专门分支同样满足,无独立分支免跑并注明;任务特别轻量时管理员可显式豁免并留痕)**:

**提供者接口约定**:输入＝分支 diff(基线分支 → 目标分支);输出＝分级缺陷清单(critical/high/medium/low,行级定位);运行要求＝独立进程、独立凭证、会话标识每次新生成不得复用。命令形态从 defaults.md 的机器初审段带出;未登记时先探测本机可用审查 CLI,探测不到则询问用户接入(接入范例见 examples/provider-opencode-review.md,含 env 包装注入环境变量、uuid 生成、cwd 适配等 world.run 细节)或免跑。

severity 归并:critical/high=候选阻塞、medium=候选建议、low 忽略。输出语言中文。**双审是硬规则、路 C 是默认增益**:失败/超时 catch 降级留痕,不阻塞验收、不替代任何一路。

**返回值**:WorkflowReport 形态(conclusion+findings[各单元:状态(候选放行/待裁定/failed)+两路结论摘要+证据]+verified+notCovered),并以 `artifact.markdown` 发布完整验收报告。

## 4. run 期间管理员职责

- **不轮询、不等待**:完成/异常通知自动到达。
- **escalation 应答(三分类)**:①事实澄清/材料补齐 → ResolveWorkflowQuestion 直答;②需用户决策 → 主对话问用户后回填;③脚本结构问题 → 改脚本 AmendWorkflow 重发。
- stall 通知(20 分钟无进展)= 信息性,run 仍在跑,不需处置;若疑似长期卡住且无 escalation,用 GetWorkflowRun 看快照确认——在跑则继续等,确认停滞则停止该 run、带材料缩小任务重开。

## 5. run 结束:终裁、合并、收尾

1. **逐单元终裁(不可让渡)**:读返回材料+验收报告 → 候选放行可否决;待裁定必裁定;冲突显式裁定写明理由;可依客观材料对定级升降(附证据)。
2. **工作树模式**:终裁通过即在主工作区合并(优先 `--ff-only`,不能快进则 `--no-ff`;冲突列清单交用户)→ 按复制清单删树内副本 → `git worktree remove` → 清 upstream 删分支 → `git worktree prune`。**普通模式**:终裁通过即收尾,交付物就位。
3. **最终汇报**:改了什么(或产出什么)、跑了哪些测试、双审情况(两路结论、冲突与裁定、路 C 结果(已跑/豁免及理由)、返工轮次)、合并与清理结果(树模式)、遗留问题与是否建议全量回归(代码类)。

## 6. 失败处置

- **provider 停止**(登录过期/模型不在计划/额度):停下与用户修因 → 续跑(已完成步骤零成本回放)。
- **脚本 errored**(通知点名脚本文件):Edit 修复 → AmendWorkflow(path)重发;不从头重写。
- **run 方向不对**:立即 AmendWorkflow,不等跑完。
- **用户主动停止**:问清意图再动。
- **审查路能力缺失**(异构候选不可用):停下问用户推荐满足条件的替代,不得静默降级单审放行。
- **执行者失败**:脚本标记 failed 交回,管理员缩小任务重开;最终汇报如实说明。

## 7. 与原版 aicode-mainother-general 的已知差异

1. **确认节奏**:原版派发前一次性问清即开跑 → 本版每 run 一次 CreateWorkflow 确认框(含阶段图与命令集)。
2. **问答机制**:QA 文档停机轮转(长任务)/会话唤醒 → escalation 直问、原地继续;QA 文档在本引擎下不再使用——审查结论由脚本汇总进返回材料与验收报告,结论性内容留档进最终汇报与(树模式)提交记录。
3. **非阻塞派发**:原版靠 `run_in_background`+轮询唤醒 → 本版 fan-out 天然并行,管理员零盯守。
4. **心跳盯梢**:删除——provider 临时错误运行时自愈;真卡住会 escalation 或 stall 通知(停滞兜底见第 4 节)。
5. **模型管理**:四问答案=启动锁定的模型名册;换模型=改脚本重发(缓存回放)。
6. **路 C 形态**:管理员外勤 CLI → 脚本 world.run 机器闸门;受 cwd 限制,首用前须实测适配;由"可选"升为"代码类默认加跑、轻量可豁免"(与原版同步调整,见 CHANGELOG)。
